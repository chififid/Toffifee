# Правила аккуратной разработки проекта

Этот файл — обязательная памятка для агента, который продолжает разработку лендинга Toffifee. Главный приоритет — сохранить аккуратную поддержку проекта и визуальное соответствие макету Figma.

## Перед изменениями

- Сначала изучить существующую разметку, SCSS, токены и JS; не переписывать работающий блок вслепую.
- Проверить, не решена ли задача уже существующим компонентом или стилем.
- Если источник — Figma, использовать точный экспорт нужного узла. Не угадывать геометрию по скриншоту, если доступен сам узел.
- После каждого заметного визуального изменения проверять страницу в браузере, а не ограничиваться чтением CSS.

## Архитектура проекта

- `src/js/main.js` — только точка инициализации. Самостоятельное поведение хранить в `src/js/modules/`, общие небольшие утилиты — в `src/js/utils/`.
- JS должен находить интерактивные узлы по `data-*`-атрибутам, а не по классам оформления. Функция инициализации обязана безопасно завершаться, если её корневого узла нет.
- Стили самостоятельных BEM-компонентов хранить в `src/scss/components/`, геометрию и декор конкретной секции — в `src/scss/sections/`.
- Не создавать глобальную переменную ради единственного значения. В `_tokens.scss` выносить только повторяемые значения с общей семантикой; размеры конкретного блока хранить локально.
- Не генерировать статическое содержимое лендинга через JS. Разметка должна оставаться доступной без выполнения модулей.

## Figma и ассеты

- Для векторных декоративных элементов, стрелок, фигурных карточек и иконок использовать SVG из Figma.
- Не использовать криво обрезанные PNG, если в макете доступен чистый SVG.
- Не вырезать изображения через `object-position`, огромные отрицательные `top/left` или случайные контейнеры. Если картинка нужна без лишних частей — экспортировать правильный узел заново.
- Не дублировать один и тот же фон в нескольких местах без причины.
- Хранить ассеты по секциям: `src/assets/images/<section>/...`;
- Для декоративных изображений использовать `alt=""`, `aria-hidden="true"` и `pointer-events: none`.
- Не оставлять в проекте архивы, временные скачанные файлы и ненужные варианты ассетов.

## Декоративные растровые фоны

- Подробная обязательная инструкция находится в [`docs/decorative-backgrounds.md`](docs/decorative-backgrounds.md). Перед любым изменением hero, foliage возле слайдера или добавлением нового растрового фона прочитать её полностью.
- Для всех составных лиственных цепочек использовать только `src/assets/images/site-foliage/foliage-blue.png`; не добавлять склеенные, зеркальные, отдельно растянутые или отличающиеся только opacity варианты. Уникальный папоротник футера хранится отдельным точным экспортом `src/assets/images/footer/footer-fern.png`, не используется как сегмент этих цепочек и не получает дополнительную CSS-opacity, потому что прозрачность уже запечена в экспорте Figma.
- Собирать длинную фактуру из повторных сегментов с перекрывающимися зонами fade. Не стыковать прозрачные торцы и не скрывать края через `border-radius`.
- Слой, crop-рамку, естественное изображение и маски брать из `src/scss/_decorative-background.scss`; не размножать их базовые свойства по секциям. Сохранять независимые слои фона, сетки и контента.
- Перед передачей обязательно скрыть контент секции и проверить у каждого повёрнутого сегмента все четыре локальных торца, внутренний стык, начало и конец цепочки. Проверка только исправленного края запрещена: после любой правки полный аудит повторяется.
- Прямая горизонтальная или вертикальная линия, внезапное окончание листьев, белая щель, тёмный шов либо видимая граница crop означают, что фон не готов, даже если дефект частично закрыт контентом.
- После фонового аудита проверить композицию с контентом при обычном и широком viewport, затем выполнить `npm run check`.

## Разметка и размеры

- Предпочитать flex/grid, `gap`, padding, margin, `max-width` и `width: 100%`.
- Не фиксировать высоты блоков через `height` или `min-height`, если это не обязательный размер настоящего ассета/контрола.
- Не задавать одну и ту же ширину/отступ десятками повторяющихся абсолютных значений.
- Для изображений сохранять пропорции через `aspect-ratio` или естественный размер; не хардкодить одновременно случайные width и height.
- Абсолютное позиционирование использовать только для декоративных элементов, которые привязаны к ближайшему смысловому контейнеру. Не считать координаты от верхнего края страницы.
- Не использовать конструкции вроде `width: min(calc(100% - ...), ...)` там, где достаточно padding контейнера и `max-width`.
- Сохранять существующую структуру BEM: секция, элемент `__element`, модификатор `--modifier`.
- Общие цвета, тени, радиусы и длительности хранить в `src/scss/_tokens.scss`, а не размножать по файлам.
- Не возвращать глобальный `min-width` странице. Базовая desktop-вёрстка должна естественно сжиматься за счёт fluid gutter, `minmax(0, 1fr)` и ограниченных `max-width`; изменение композиции относится к отдельному адаптивному этапу.
- Точные размеры допустимы для контролов, экспортированных ассетов и локальной декоративной геометрии. Не использовать их для искусственного удержания всей страницы на одной ширине.

## Интерактивность и доступность

- Loader и основное содержимое должны работать по progressive enhancement: ошибка JS не может навсегда заблокировать страницу.
- Для настоящих tabs поддерживать `aria-selected`, roving `tabindex`, связи `aria-controls`/`aria-labelledby` и клавиши стрелок, Home и End.
- Декоративным изображениям задавать `alt=""`, `aria-hidden="true"` и `pointer-events: none`; если вся декоративная группа уже скрыта через `aria-hidden`, не дублировать доступную семантику на дочерних элементах.
- Не объявлять визуальный переключатель ARIA-вкладками, пока он не управляет настоящей tabpanel.

## Кнопки и анимации

- Кнопки не должны двигаться, менять padding, width или transform при hover.

## Текст, шрифты и порядок слоёв

- Использовать подключённые локальные Impact/Geologica/Alumni Sans; не добавлять дублирующие шрифты.
- Выделения в тексте делать настоящим `<strong>` или отдельным смысловым элементом, а не случайной фиксированной шириной.
- Следить за `z-index`: лица и содержимое карточек должны быть выше декоративных слоёв, сердечки и стрелки — ниже текста, если так задумано макетом.

## Проверка перед передачей

Обязательно выполнить:

```bash
npm run check
```

Команда должна пройти lint, stylelint, Prettier и production build. Для визуальных правок дополнительно открыть локальный сервер и проверить минимум: обычный размер, уменьшенный масштаб, hover/focus, прокрутку, FAQ, карусели и контакты.

Контрольные desktop viewport: 1280 px как визуальный эталон, 1600 px для широкого состояния, 1180 и 1024 px для проверки естественного сжатия без отдельного адаптива. Проверять отсутствие горизонтального переполнения содержимого и обрезанных заголовков.

Не считать задачу готовой, если сборка проходит, но на скриншоте видны обрезанные края, случайная подложка PNG, скачок тени, движение кнопки или перекрытие соседнего блока.
